# 방과후 통합 매니저 — 설계안 v2 (Phase 0 확정본)

작성일: 2026-09-06 · v2 개정: 지원기간·이월정책, 자격 유효기간, 우선순위 범위, **작업공간 순서 제거(날짜 순 고정)**

이 문서는 설계 의도를 담습니다. 실제 스키마의 원본은
`src-tauri/migrations/001_init.sql`이며, 이 문서는 "왜 그렇게 했는가"를 설명합니다.

핵심 네 가지 — **① 데이터 모델 ② 지원기간·이월을 반영한 잔액 계산
③ 부서·항목 우선순위 차감 ④ 이용권+자유수강권 동시 보유** — 는 4·5·6·7장에
알고리즘 수준으로 적었습니다. 확정된 판단은 0장에 모았습니다.

## 0. 확정된 결정 (v2 — 검토 반영 완료)

v1의 제안 중 **①·②·⑥**은 검토 결과 아래와 같이 바뀌었습니다. 나머지는 제안대로 확정입니다.

### (1) 이용권 한도는 "연간 총액"이 아니라 **연간 + 지원기간 + 이월정책** — v2 변경

```
방과후 이용권
  연간 총 한도   500,000원
  이월정책       이월 / 소멸
  ├─ 지원기간 1  1학기  (3/1 ~ 8/31)  한도 250,000원
  └─ 지원기간 2  2학기  (9/1 ~ 2/28)  한도 250,000원
```

- **정책 A(소멸)** — 1학기 250,000 중 200,000 사용 → 2학기 사용 가능액 **250,000**
- **정책 B(이월)** — 같은 상황에서 2학기 사용 가능액 **300,000**
- 어느 정책이든 **연간 500,000원을 넘길 수 없습니다.**

DB에 `semester1_limit` 같은 컬럼을 두지 않습니다. `support_period` 표에
행을 몇 개 넣느냐로 결정되므로, 학기제가 아닌 분기제·기수제로 바뀌어도
스키마를 고치지 않습니다. **지원기간이 하나도 없으면 = 연간 한도 하나로 운영**이며
v1 구조와 결과가 같습니다(하위 호환).

자유수강권도 **같은 구조**를 씁니다. 기간을 안 만들면 연간 한도 하나로 동작합니다.

### (2) 지원자격은 명단이 아니라 **기간**을 가진다 — v2 변경

전입·전출·신규 선정·지원 중지가 학년도 중에 일어납니다.
`support_eligibility`에 `valid_from` / `valid_to`(둘 다 nullable)를 두고,
**작업공간 기간과 겹치면 그 작업공간에서 유효**한 것으로 봅니다.

```
유효 = (valid_from IS NULL OR valid_from <= 작업공간.종료일)
   AND (valid_to   IS NULL OR valid_to   >= 작업공간.시작일)
```

`NULL`은 "학년도 내내"입니다. 명단만 올리면 지금까지처럼 동작하고,
중도 변동이 있는 학생만 날짜를 넣습니다. 이용권·자유수강권 모두 같은 구조입니다.

### (3) 이용권 자격 = 명단 등재 AND 대상학년 — 확정, 단 **자동 삭제 없음**

대상학년과 명단이 어긋나면 **경고만** 합니다. 명단을 지우거나 고치지 않습니다.

> ⚠ 방과후 이용권 대상학년이 아닌 학생 3명이 대상자 명단에 포함되어 있습니다. [목록 보기]

정책(대상학년)을 바꿨다고 기존 명단을 건드리지 않습니다. 정산에서는 지원되지 않고
경고 목록에 남습니다.

### (4) 제도 적용순서 = 이용권 → 자유수강권 → 수익자 — 확정

이용권이 소진되었다는 이유로 **즉시 수익자로 확정하지 않습니다.**
다음 제도(자유수강권)의 적용 가능 여부를 반드시 확인한 뒤 남은 금액만 학부모 부담이
됩니다. 순서는 `app_setting.program_order`(기본 `VOUCHER,FREE_VOUCHER`)로 바꿉니다.

### (5) 발생 원인(origin) 추적 — 확정

| origin | 뜻 |
|---|---|
| `PLAIN` | 일반 수익자 (처음부터 지원 대상 아님) |
| `VOUCHER_EXHAUSTED` | 방과후 이용권 소진 후 발생 |
| `FREE_EXHAUSTED` | 자유수강권 소진 후 발생 (이용권까지 있던 학생이면 둘 다 소진한 것) |

`fund`는 품의·정산표의 기준이고, `origin`은 "왜 학부모 부담이 되었는가"의 추적용입니다.

### (6) 우선순위는 **부서·항목 둘 다 작업공간 소속** — v2 변경

v1에서 비용항목 우선순위를 학년도에 두려 했으나, 작업공간별 실제 수강 데이터에
적용하는 것이 맞으므로 **둘 다 `workspace_id`에 붙입니다.**

- 부서 우선순위 목록에는 **그 작업공간에서 이용권 대상자가 실제 수강 중인 부서**만 뜹니다.
- 비용항목 기본값 `강사료 > 수용비 > 교재비 > 재료비`, 사용자가 변경 가능.
- 새 작업공간을 만들면 직전 작업공간의 순서를 **부서명으로 맞춰 승계**하고,
  새로 생긴 부서는 맨 뒤에 붙습니다.

### (7) 수강 취소·금액 수정은 원장을 건드리지 않는다 — 확정

원본(`enrollment` / `charge`)만 바뀝니다. 사용자가 그 작업공간을 다시 정산하면
새 `settlement`가 `is_latest=1`이 되고, 과거 정산은 감사용으로 남되
**계산에는 `is_latest=1`만 쓰입니다.**

### (8) 선행 정산 변경은 자동 재계산하지 않고 경고만 — 확정 (8장)

`지원금 잔액 조회`(항상 최신 질의)와 `저장된 정산결과`(그때의 스냅샷)를 분리합니다.
둘이 어긋나면 그 사실을 화면에 띄우고, 다시 만드는 것은 사람이 결정합니다.

### (9) 금액은 전부 정수(원), 나눗셈 없음 — 확정

`min(잔액, 금액)`의 뺄셈만 씁니다. 반올림 오차가 원천적으로 없습니다.
불변식: `Σ(재원별 배분액) = 그 수강·그 항목의 금액`.

### (10) 학생 식별자는 내부 id — 확정

`student.id`가 학년도 안에서 고정됩니다. Excel 업로드는 `학년+반+번호`로 찾아
갱신하고, 없는 행만 추가합니다.

## 1. 기술 구조

| 항목 | 선택 | 이유 |
|---|---|---|
| 셸 | **Tauri 2** | 설치 파일 5MB대, 시작 1초 이내. Electron 대비 압도적으로 가벼움 |
| 화면 | **React 18 + TypeScript + Vite** | 보결 배정 시스템과 동일 — 쌓인 컴포넌트·CSS를 재사용 |
| 상태 | **@tanstack/react-query** | 서버(=로컬 DB) 상태 캐시·무효화를 한 곳에서 |
| DB | **SQLite (rusqlite, bundled)** | 파일 하나. 외부 서버·클라우드 없음 |
| 정산 | **Rust (`domain/` 모듈)** | UI와 완전히 분리, `cargo test`로 경계값 검증 |
| Excel 읽기 | **calamine** | .xlsx/.xls 모두. Rust에서 처리해 브라우저 메모리 한계를 피함 |
| Excel 쓰기 | **rust_xlsxwriter** | 열 너비·서식·숫자형식 지정이 정확함(§27 열 너비 10) |
| 업데이트 | **tauri-plugin-updater + GitHub Releases** | 보결 배정 시스템에서 검증된 방식 |

### Excel을 Rust에서 처리하는 이유

프런트엔드 `xlsx`(SheetJS) 계열은 (a) npm 배포판이 오래되어 보안 권고가 붙어 있고,
(b) 전교생 × 수강 데이터가 커지면 브라우저 메모리에 통째로 올라가며,
(c) 열 너비·숫자 서식 제어가 약합니다. Rust에서 처리하면 파일 경로만 오가므로
화면은 진행 상태만 그리면 됩니다.

### 폴더 구조 (보결 배정 시스템과 동일한 계층)

```
src/                      화면
  components/             공용 UI (Button, Modal, DataTable, …)
  features/<도메인>/       화면별 구현
  ipc/                    invoke 래퍼 (타입 정의는 여기 한 곳)
  lib/                    포맷터·훅
src-tauri/
  migrations/00N_*.sql    스키마 (한 번 배포된 파일은 절대 수정 금지)
  src/db/                 연결·마이그레이션
  src/repo/               SQL — 표 하나당 한 파일
  src/domain/             정산 엔진·검증 (DB 의존 없음, 순수 함수)
  src/excel/              import(calamine) / export(rust_xlsxwriter)
  src/commands/           #[tauri::command] — 얇게, 로직 없음
```

**`domain/`은 `rusqlite`를 import하지 않습니다.** 입력은 구조체, 출력도 구조체입니다.
그래야 정산 엔진을 DB 없이 테스트할 수 있습니다.

### 저장 위치 분리 (§3)

| 대상 | 위치 |
|---|---|
| 실행 파일 | `%LOCALAPPDATA%\방과후 통합 매니저\` (NSIS currentUser) |
| 업무 DB | `%APPDATA%\kr.school.afterschool\afterschool.db` |
| 백업 | 위 폴더의 `backups\` |
| Excel 출력 | 위 폴더의 `exports\` (저장 후 [폴더 열기] 제공) |

업데이트는 실행 파일만 교체하므로 **DB는 손대지 않습니다.** 마이그레이션은
버전이 올라간 경우에만 적용되고, 적용 직전 DB 파일을 `backups/`에 자동 복사합니다.

## 3. 재원(fund) 정의 — 코드에서 쓰는 유일한 어휘

```rust
enum Fund {
    SelfPay,      // SELF_PAY      일반 수익자 부담금
    Voucher,      // VOUCHER       방과후 이용권 사용액
    VoucherOver,  // VOUCHER_OVER  이용권 한도 초과분(학부모 부담)
    FreeVoucher,  // FREE_VOUCHER  자유수강권 사용액
}
```

`3학년`이라는 말은 **DB·엔진 어디에도 없습니다.** Excel 출력 시에만
`support_policy.target_grades`를 읽어 `3학년 지원금` 같은 이름표를 만듭니다(9장).
대상학년이 `3,4`로 바뀌면 이름표가 `3·4학년 지원금`으로 저절로 바뀝니다.

`origin`은 재원 안의 사연을 따로 남기는 보조 컬럼입니다.

| origin | 뜻 |
|---|---|
| `PLAIN` | 처음부터 수익자 부담 |
| `VOUCHER_EXHAUSTED` | 이용권을 다 써서 넘어옴 |
| `FREE_EXHAUSTED` | 자유수강권을 다 써서 넘어옴 |

`fund`는 품의·정산표의 기준이고, `origin`은 수익자 탭의 내역 구분용입니다.

## 4. SQLite 데이터 모델 (최종)

### 4-1. 소속 관계

```
academic_year (2026학년도)
 ├─ support_policy      (제도별: 연간한도 · 이월정책 · 대상학년)
 │   └─ support_period  (1학기 250,000 / 2학기 250,000 …)   ← v2 신설
 ├─ support_grant       (학생별 예외 한도: 연간 또는 특정 기간)
 ├─ support_eligibility (학생 × 제도 × 유효기간)              ← v2 기간 추가
 ├─ student             (전교생)
 ├─ change_log
 └─ workspace           (2026년 4월 / 여름방학 …)
     ├─ department → department_fee
     ├─ dept_priority        ← 작업공간 소속
     ├─ item_priority        ← v2: 작업공간 소속으로 이동
     ├─ enrollment → charge
     └─ settlement → settlement_alloc
cost_item   (전역 카탈로그: 강사료·수용비·교재비·재료비)
app_setting (전역)
```

### 4-2. 표 정의

제약조건 전체는 `src-tauri/migrations/001_init.sql`에 있습니다. 여기서는 의도를 적습니다.

#### academic_year
| 컬럼 | 설명 |
|---|---|
| id, year(UNIQUE), name | `2026`, `2026학년도` |
| start_date, end_date | 기본 `2026-03-01` ~ `2027-02-28` |
| data_version | 정산에 영향을 주는 학년도 자료가 바뀌면 +1 (8장) |
| is_current | 현재 학년도 1개 |

#### workspace
| 컬럼 | 설명 |
|---|---|
| id, year_id, name | `2026년 4월`, `여름방학` — 자유 입력 |
| start_date, end_date | `YYYY-MM-DD` |
| data_version | 이 작업공간 자료가 바뀌면 +1 |
| is_current | 상단 고정 표시용 |
| INDEX | (year_id, start_date, end_date, id) — 목록과 누적 계산이 같이 쓰는 정렬 |

> **순서 컬럼을 두지 않습니다** (v2 개정).
>
> 목록에 보이는 차례도, 정산에서 "앞선 작업공간"을 정하는 차례도 언제나
> **`(시작일, 종료일, id)`** 하나입니다. 사람이 만질 수 있는 `seq`를 두면
> 화면 순서와 누적 순서가 갈릴 수 있고, 그때 나오는 오차는 조용해서
> 알아채기 어렵습니다. 순서를 바꾸고 싶으면 날짜를 고칩니다 — 날짜가 곧 순서입니다.
>
> 시작일이 같으면 종료일, 그래도 같으면 `id`로 갈립니다(등록 순서). 세 값을 함께
> 견주므로 순서가 흔들리지 않습니다.
>

## 5. 지원금 잔액 계산 — 핵심 ② (v2 전면 개정)

관계는 이렇습니다.

```
학년도 → 지원정책 → 지원기간 → (이월정책) → 작업공간 → 최신 정산결과
```

### 5-0. 원장을 표로 두지 않는다 (유지)

"학생별 사용 원장"을 만들고 정산할 때마다 더하고 빼는 방식은 취소·재정산·복원이
한 번이라도 꼬이면 진실이 아니게 됩니다. **원장은 표가 아니라 질의입니다.**

```sql
-- 학생 S가 작업공간 집합 WS에서 실제로 쓴 이용권 금액
SELECT COALESCE(SUM(a.amount), 0)
FROM settlement_alloc a
JOIN settlement s ON s.id = a.settlement_id AND s.is_latest = 1
WHERE s.workspace_id IN (:WS) AND a.student_id = :S AND a.fund = 'VOUCHER';
```

바뀐 것은 **"어떤 작업공간을 어떤 한도에 견주는가"** 뿐입니다.

### 5-1. 작업공간이 속한 지원기간

```
그 작업공간의 시작일을 포함하는 지원기간
  없으면 → 기간과 겹치는 것 중 겹치는 날짜가 가장 많은 기간
  그래도 없으면 → 기간 없음(연간 한도만 적용) + 경고
```

지원기간이 아예 정의되지 않은 정책은 **"학년도 전체가 하나의 기간"** 으로 봅니다.
그러면 아래 식이 그대로 v1(연간 총액 누적)과 같아집니다.

### 5-2. 사용 가능액 계산식

작업공간 `W`(기간 `P`), 학생 `S`, 제도 `G`에 대해.
"앞선"은 언제나 `(시작일, 종료일, id)` 비교입니다 — 목록 화면과 같은 순서입니다.

```
limit(k)      = grant(S, G, 기간k) ?? 기간k.limit_amount        -- 기간 한도
annual        = grant(S, G, NULL)  ?? policy.annual_limit        -- 연간 한도
used(k)       = 기간 k에 속한 작업공간들의 최신 정산 VOUCHER 합
used_in_P_before = 기간 P 안에서 W보다 앞선 작업공간들의 사용액
used_all_before  = Σ_{k<P} used(k) + used_in_P_before

carry_in = carryover ? max(0, Σ_{k<P} limit(k) − Σ_{k<P} used(k)) : 0

가용액(W) = max(0, min(
      limit(P) + carry_in − used_in_P_before,   -- 기간 한도 (+이월) 에서 남은 몫
      annual   − used_all_before                -- 연간 한도에서 남은 몫
))
```

**두 한도 중 작은 쪽**이 실제 가용액입니다. 이월을 허용해도 연간 총액을 넘길 수
없다는 요구가 `min`의 두 번째 항 하나로 지켜집니다.

#### 검증 — 요구사항의 예시 그대로

연간 500,000 / 1학기 250,000 / 2학기 250,000, 1학기 사용 200,000, 2학기 첫 작업공간:

| | 정책 A (소멸) | 정책 B (이월) |
|---|---:|---:|
| carry_in | 0 | max(0, 250,000−200,000) = **50,000** |
| 기간 몫 | 250,000 + 0 − 0 = 250,000 | 250,000 + 50,000 − 0 = **300,000** |
| 연간 몫 | 500,000 − 200,000 = 300,000 | 500,000 − 200,000 = 300,000 |
| **가용액** | **250,000** ✓ | **300,000** ✓ |

1학기를 한 푼도 안 썼다면 정책 B의 기간 몫은 500,000, 연간 몫도 500,000 →
가용액 500,000이며 **연간 한도를 넘지 않습니다** ✓

1학기 사용액이 나중에 230,000으로 늘면 carry_in은 20,000, 가용액은 270,000으로
자동으로 바뀝니다 — 이월액을 어디에도 저장해 두지 않기 때문입니다.

#### 기간 안에 작업공간이 여럿일 때

1학기에 3·4·5·6·7월 작업공간이 있으면, 5월을 정산할 때
`used_in_P_before`는 3·4월의 최신 정산 사용액 합입니다.
`limit(P)`는 기간 전체(250,000)이므로 **월마다 한도가 새로 생기지 않습니다.**

### 5-3. 화면에 보여줄 값 (§21)

| 표시 | 계산 |
|---|---|
| 연간 총 지원금 | `annual` |
| 지원기간 | `P.name` (`1학기`) |
| 기간 한도 | `limit(P)` |
| 이월액 | `carry_in` (소멸 정책이면 `0`, 회색으로 `이월 없음`) |
| 기간 사용 가능액 | `limit(P) + carry_in` (연간 몫에 잘리면 잘린 값과 함께 표시) |
| 이전 사용액 | `used_in_P_before` |
| 현재 사용액 | 이번 정산의 `VOUCHER` 합 |
| 기간 잔액 | `가용액 − 현재 사용액` |
| 연간 누적 사용액 | `used_all_before + 현재 사용액` |
| 연간 잔액 | `annual − 연간 누적 사용액` |

### 5-4. 아직 정산하지 않은 선행 작업공간

`is_latest=1` 정산이 없는 선행 작업공간은 사용액 0으로 계산됩니다.
잔액이 실제보다 많아 보일 수 있으므로 정산 생성 화면에 띄웁니다.

> ⚠ 앞선 작업공간 **2026년 4월**의 정산이 아직 없습니다. 이전 사용액이 0으로 계산됩니다.

### 5-5. 자유수강권

**같은 함수를 씁니다.** 기간을 만들지 않으면 연간 한도 하나로 동작하고,
학기별로 나누고 싶으면 `support_period` 행을 넣으면 됩니다.
`carryover`도 제도별로 따로 정합니다.

### 5-6. 설정 화면 — 회계 구조를 몰라도 정책만 보고 설정한다

`시스템 › 학년도 지원금 설정`

```
┌ 방과후 이용권 ───────────────────────────────────────────┐
│  연간 지원한도   [    500,000 ] 원                        │
│  대상 학년       [3학년 ✓] [4학년 ] [5학년 ] …            │
│                                                          │
│  지원기간                                    [+ 기간 추가] │
│  ┌──────────┬────────────┬────────────┬───────────┬───┐  │
│  │ 이름     │ 시작일     │ 종료일     │ 지원한도  │   │  │
│  │ 1학기    │ 2026-03-01 │ 2026-08-31 │  250,000  │ ✕ │  │
│  │ 2학기    │ 2026-09-01 │ 2027-02-28 │  250,000  │ ✕ │  │
│  └──────────┴────────────┴────────────┴───────────┴───┘  │
│  기간 한도 합계 500,000원 / 연간 500,000원  ✓            │
│                                                          │
│  미사용 지원금 처리                                       │
│   ○ 다음 지원기간으로 이월                                │
│   ● 지원기간 종료 시 소멸                                 │
│                                                          │
│  ℹ 지원기간을 만들지 않으면 연간 한도 하나로 운영됩니다.   │
└──────────────────────────────────────────────────────────┘
```

화면이 대신 확인해 주는 것:

- 기간 한도 합계가 연간 한도와 다르면 안내 (`합계 500,000 / 연간 450,000 — 확인 필요`).
  **막지는 않습니다.** 실제로 다르게 운영하는 학교가 있을 수 있고,
  계산식의 `min`이 어느 쪽이든 안전하게 처리합니다.
- 기간이 서로 겹치거나 빈 날짜가 있으면 그 자리에서 표시.
- 어떤 작업공간이 어느 기간에 속하는지 목록으로 보여줌
  (`2026년 4월 → 1학기`, `여름방학 → 1학기`, `9월 → 2학기`).
- 이월 라디오를 바꾸면 **저장 전에** 영향을 미리 보여줌
  (`이월로 바꾸면 2학기 대상 학생 12명의 사용 가능액이 늘어납니다`).

학생별 예외 한도(`support_grant`)는 같은 화면의 `[학생별 예외]` 팝업에서
`연간` 또는 `특정 기간`을 골라 입력합니다.

## 6. 부서·항목 우선순위 차감 — 핵심 ③

### 계산 단위: (수강 × 비용항목) 하나

한 학생의 이번 작업공간 금액을 전부 펼쳐 **한 줄로 세운 뒤 앞에서부터 채웁니다.**

```
정렬 키 = (부서 우선순위, 항목 우선순위, department_id, item_code)
          ↑ 둘 다 그 작업공간의 설정 (v2)
```

예 — 부서 `로봇과학 > 미술 > 축구`, 항목 `강사료 > 수용비 > 교재비 > 재료비`,
3학년 김OO의 이번 작업공간 이용권 가용액 100,000원(5장에서 계산):

| # | 부서 | 항목 | 금액 | 이용권 사용 | 남는 금액 |
|---|---|---|---:|---:|---:|
| 1 | 로봇과학 | 강사료 | 40,000 | 40,000 | 0 |
| 2 | 로봇과학 | 교재비 | 30,000 | 30,000 | 0 |
| 3 | 미술 | 강사료 | 25,000 | 25,000 | 0 |
| 4 | 미술 | 재료비 | 15,000 | **5,000** | **10,000** |
| 5 | 축구 | 강사료 | 20,000 | 0 | 20,000 |
| | | 합계 | 130,000 | 100,000 | 30,000 |

4번에서 한도가 끊깁니다. **한 줄이 쪼개지는 것을 허용**합니다 — 쪼개지 않으면
잔액 5,000원이 영원히 남아 잔액과 실제가 어긋납니다. 4번은
`VOUCHER 5,000` + (다음 제도 또는) `VOUCHER_OVER 10,000` 두 행으로 저장됩니다.

### 엔진 (Rust, `domain::settle` — DB 의존 없는 순수 함수)

```rust
pub fn settle_student(input: &StudentInput, cfg: &Config) -> Vec<Alloc> {
    // 1) 차감 단위를 우선순위대로 세운다 (0원 항목 제외)
    let mut units: Vec<Unit> = input.charges.iter()
        .filter(|c| c.amount > 0)
        .map(|c| Unit::new(
            (cfg.dept_rank(c.department_id),   // 목록에 없으면 usize::MAX
             cfg.item_rank(c.item_code),
             c.department_id, c.item_code),
            c.amount))
        .collect();
    units.sort_by(|a, b| a.key.cmp(&b.key));

    let mut out = Vec::new();
    let mut last_exhausted: Option<Program> = None;

    // 2) 제도를 설정된 순서대로 소진한다 (기본 VOUCHER → FREE_VOUCHER)
    //    ── 이용권이 끝났다고 여기서 수익자로 확정하지 않는다
    for program in &cfg.program_order {
        if !input.eligible(*program) { continue; }     // 자격 기간까지 확인 (0-2)
        let mut left = input.available(*program);      // 5장의 가용액
        for u in units.iter_mut() {
            if left == 0 { break; }
            let use_amt = min(left, u.remain);
            if use_amt > 0 {
                out.push(Alloc::new(u, program.fund(), Origin::Plain, use_amt));
                u.remain -= use_amt;
                left     -= use_amt;
            }
        }
        last_exhausted = Some(*program);               // 이 제도를 거쳤다
    }

    // 3) 모든 제도를 거치고도 남은 금액만 학부모 부담이 된다
    let fund = if input.eligible(Program::Voucher) { Fund::VoucherOver } else { Fund::SelfPay };
    let origin = match last_exhausted {
        Some(Program::FreeVoucher) => Origin::FreeExhausted,
        Some(Program::Voucher)     => Origin::VoucherExhausted,
        None                       => Origin::Plain,
    };
    for u in units.iter().filter(|u| u.remain > 0) {
        out.push(Alloc::new(u, fund, origin, u.remain));
    }
    out
}
```

**불변식**(모든 테스트에서 검사):
`Σ out[수강][항목] == charge[수강][항목]` — 1원도 사라지거나 생기지 않습니다.

### 반드시 넣을 경계값 테스트 (Phase 3, 화면보다 먼저 작성)

| # | 상황 | 기대 |
|---|---|---|
| 1 | 가용액 0 | 전액 VOUCHER_OVER |
| 2 | 가용액 = 총액 | 전액 VOUCHER, 잔액 0 |
| 3 | 가용액이 한 항목 중간에서 끊김 | 그 항목이 두 행으로 분할 |
| 4 | 기간 한도를 이미 다 씀 | 가용액 0, 음수 없음 |
| 5 | 한도를 사후에 낮춰 이전 사용 > 한도 | 가용액 0 |
| 6 | **이월 정책 A/B 비교** | 5-2 표의 250,000 / 300,000 |
| 7 | **이월액이 연간 한도에 잘림** | `min` 두 번째 항이 이김 |
| 8 | **지원기간 0개** | 연간 한도 하나로 동작 |
| 9 | 기간 안 작업공간 3개 | 월마다 한도가 새로 생기지 않음 |

## 7. 이용권 + 자유수강권 동시 보유 — 핵심 ④

6장 엔진의 2번 반복문이 그대로 처리합니다. **이용권 소진이 곧 학부모 부담 확정이
아닙니다** — 반복문이 끝나기 전에는 3번 블록으로 내려가지 않습니다.

예 — 3학년 박OO, 이번 작업공간 총액 200,000원.
이용권: 2학기 기간 한도 250,000 + 이월 0, 기간 내 이전 사용 180,000 → **가용 70,000**
자유수강권: 연간 한도 60,000, 이전 사용 0 → **가용 60,000**

| 단계 | 계산 | 결과 |
|---|---|---|
| 이용권 차감 | 우선순위 순으로 70,000 | `VOUCHER 70,000` |
| 자유수강권 차감 | 남은 130,000 중 60,000 | `FREE_VOUCHER 60,000` |
| 남은 금액 | 130,000 − 60,000 | `VOUCHER_OVER 70,000` (origin=`FREE_EXHAUSTED`) |
| 합계 검증 | 70,000+60,000+70,000 | **200,000 ✓** |

같은 학생이 이용권 대상이 아니고 자유수강권만 있었다면 마지막 줄은
`SELF_PAY 70,000 (origin=FREE_EXHAUSTED)`이 되어 품의의 `수익자` 열로 갑니다.

`origin` 덕분에 수익자 탭에서 **일반 / 이용권 소진 후 / 자유수강권 소진 후**를
구분해 보여줄 수 있습니다(§20).

학생 상세정보(§23)의 `해당없음`은 **그 작업공간 기간에 유효한 자격 행이 있는지**로
판단합니다 — 금액이 0원인 것과 자격이 없는 것을 절대 같게 표시하지 않습니다.

## 8. 정산 스냅샷과 "최신 여부" — §17·§49

`지원금 잔액 조회`(언제나 최신 자료로 다시 계산)와 `저장된 정산결과`(그때의 스냅샷)를
분리합니다. 둘이 어긋나면 그 사실만 알리고, 다시 만드는 것은 사람이 결정합니다.

### 자료 버전 (트리거로 자동 증가)

```sql
CREATE TRIGGER charge_bump AFTER UPDATE ON charge BEGIN
  UPDATE workspace SET data_version = data_version + 1
   WHERE id = (SELECT workspace_id FROM enrollment WHERE id = NEW.enrollment_id);
END;
```

| 버전 | 올리는 변경 |
|---|---|
| `workspace.data_version` | department, department_fee, enrollment, charge, dept_priority, item_priority |
| `academic_year.data_version` | support_policy, **support_period**, support_grant, support_eligibility, **student.grade** |

`student`는 **학년이 바뀔 때만** 올립니다. 이름·반·번호 수정은 금액에 영향이 없는데
그때마다 경고가 뜨면 사람이 경고를 무시하게 됩니다.

**응용 코드가 아니라 트리거인 이유**: 나중에 기능을 추가하다 버전 올리기를 빠뜨리면
조용히 낡은 숫자를 보게 됩니다. 트리거는 잊을 수가 없습니다.

### 낡음 판정 — 값 세 개 비교, 재계산 없음

정산은 만들 때 `ws_data_version`, `year_data_version`,
그리고 **선행 작업공간 전부**의 `wsId:정산id:생성시각` 목록(`prior_key`)을 저장합니다.
선행 작업공간이 새로 정산되거나, 정산이 사라지거나, 순서가 바뀌면 이 문자열이 달라집니다.

| 조건 | 표시 |
|---|---|
| 정산 없음 | `정산 데이터가 없습니다. [정산 데이터 생성]을 눌러 주세요.` |
| `ws_data_version` 다름 | `⚠ 정산 이후 수강·부서 자료가 변경되었습니다. 다시 생성해 주세요.` |
| `year_data_version` 다름 | `⚠ 정산 이후 지원대상·지원금 설정이 변경되었습니다. 다시 생성해 주세요.` |
| `prior_key` 다름 — 같은 지원기간 | `⚠ 선행 작업공간(2026년 4월)의 정산이 변경되었습니다. 현재 작업공간의 정산 데이터를 다시 생성해 주세요.` |
| `prior_key` 다름 — 이전 지원기간 | `⚠ 선행 지원기간(1학기)의 정산이 변경되어 이월액이 달라졌습니다. 다시 정산해 주세요.` |
| 전부 같음 | `✓ 2026-09-06 14:20 생성 · 최신` |

선행을 다시 정산해도 후행을 **자동으로 다시 계산하지 않습니다** — 사람이 모르는
사이에 확정된 숫자가 바뀌는 편이 훨씬 위험합니다.

### 정산 생성 트랜잭션

```
BEGIN IMMEDIATE
  1. 입력 적재: ACTIVE 수강 + charge + 학생 + 유효 자격 + 정책/기간/예외 + 우선순위
  2. 학생별 가용액 계산 (5장)
  3. domain::settle 실행 (DB 접근 없음)
  4. 불변식 검사 — 실패하면 ROLLBACK, 아무것도 저장하지 않음
  5. 기존 is_latest=0, 새 settlement + settlement_alloc 저장
COMMIT
```

이전 정산 행은 **지우지 않습니다.** 감사·변경이력 확인에 필요하고,
계산에는 `is_latest=1`만 쓰이므로 남아 있어도 영향이 없습니다.

## 9. 정산 결과 화면과 품의 집계

### 9-1. 생성 요약 (§18)

`settlement_alloc`을 `item_code × fund`로 GROUP BY 한 것이 그대로 표입니다.

| 항목 | 수익자 부담금 | 이용권 사용액 | 이용권 초과금 | 자유수강권 사용액 | 합계 |
|---|---:|---:|---:|---:|---:|
| 강사료 | SELF_PAY | VOUCHER | VOUCHER_OVER | FREE_VOUCHER | 행 합 |
| … | | | | | |
| 합계 | | | | | **총액** |

우하단 총액은 `Σ charge.amount`와 반드시 같습니다. 다르면 화면에 붉게 띄웁니다.

### 9-2. 세 탭

| 탭 | 필터 | 비고 |
|---|---|---|
| 수익자 | `fund IN (SELF_PAY, VOUCHER_OVER)` | 정상 지원 중인 이용권 금액은 뺍니다(§20). `origin`으로 `일반 / 이용권 초과 / 자유수강권 초과` 구분 표시 |
| 방과후 이용권 | `fund IN (VOUCHER, VOUCHER_OVER)` | 사용금액 4열 + 초과금액 4열로 피벗. 우측에 5-3 표의 지원기간·기간한도·이월액·이전·현재·기간잔액·연간잔액 |
| 자유수강권 | `fund = FREE_VOUCHER` | 초과분은 이 탭에 없고 수익자 탭에 있습니다 |

### 9-3. 품의 (§24·§25)

**부서 × 재원** 피벗입니다. 학생은 완전히 사라집니다.

```sql
SELECT d.name || d.class_name AS dept, a.fund, SUM(a.amount)
FROM settlement_alloc a JOIN department d ON d.id = a.department_id
WHERE a.settlement_id = :sid
  AND a.item_code IN (:선택한 품의 항목)     -- 강사료 / 수용비 / 교재비 / 재료비 / (교재비+재료비)
GROUP BY d.id, a.fund;
```

열 이름표는 출력할 때 `target_grades`로 만듭니다.

| 재원 | 이름표 규칙 | `target_grades='3'`일 때 |
|---|---|---|
| SELF_PAY | `수익자(<대상학년을 뺀 나머지 학년>)` | `수익자(1,2,4,5,6학년)` |
| VOUCHER_OVER | `<대상학년> 초과금` | `3학년 초과금` |
| VOUCHER | `<대상학년> 지원금` | `3학년 지원금` |
| FREE_VOUCHER | `자유수강권` | `자유수강권` |

"나머지 학년"은 학생정보에 실제로 존재하는 학년에서 대상학년을 뺀 값입니다.
`target_grades='3,4'`가 되면 자동으로 `수익자(1,2,5,6학년)` / `3·4학년 지원금`이 됩니다.
`support_policy.label_fund`에 직접 써 넣으면 그 값이 우선합니다.

마지막 열 = 부서별 합계, 마지막 행 = 열별 총합, 인원수 열은 없습니다(§24).

**계산과 서식을 분리합니다.** `domain::proposal`이 숫자만 만들고
`excel::proposal`이 이름표·열 순서·서식을 붙입니다. 학교 양식이 바뀌면
후자만 고칩니다(§26).

## 17. Phase 3 구현 메모 (2026-09-06)

### 정산 엔진 (`domain/settle.rs`)

DB에 의존하지 않는 순수 함수다. 입력은 `(학생, charge 목록, 제도별 가용액)`,
출력은 `(재원별 배분, 제도별 사용액)`이다.

```
1) charge를 (부서순위, 항목순위, 부서id, 항목코드, 수강id)로 한 줄에 세운다
2) program_order대로 제도를 소진한다 — 한도가 항목 중간에서 끊기면 그 항목을 쪼갠다
3) 모든 제도를 거친 뒤 남은 금액만 학부모 부담이 된다
```

정렬 키에 **동점이 없다.** 그래서 같은 자료를 몇 번 정산해도 같은 결과가 나온다.
`같은_자료를_두_번_정산하면_같은_결과가_나온다`로 고정했다.

#### origin 규칙 — 전체에서 하나로 통일

`origin`은 **그 학생이 자격을 가진 제도 가운데 마지막으로 거친 것**이다.
잔액이 0이어도 자격이 있으면 거친 것으로 본다.

| 자격 | fund | origin |
|---|---|---|
| 없음 | `SELF_PAY` | `PLAIN` |
| 이용권만 | `VOUCHER_OVER` | `VOUCHER_EXHAUSTED` |
| 자유수강권만 | `SELF_PAY` | `FREE_EXHAUSTED` |
| 둘 다 | `VOUCHER_OVER` | `FREE_EXHAUSTED` |

마지막 줄이 핵심이다 — **재원은 이용권 대상자의 초과금이고, 사연은 자유수강권까지
쓴 뒤 남은 것**이라는 뜻이다. 품의는 `fund`를 보고, 수익자 탭의 내역 구분은
`origin`을 본다. 규칙을 테스트 5개(`origin_규칙_…`)로 못 박았다.

### 가용액 계산에 더한 것

`used_outside_before` — 어느 지원기간에도 속하지 않는 앞선 작업공간의 사용액.
**연간 몫에서만** 뺀다. 기간 밖 운영은 설정 실수일 가능성이 높지만, 그 금액이
연간 한도 계산에서 사라지면 안 되기 때문이다. 정산 전 검사에서 경고로도 알린다.

### 학생별 예외 한도의 뜻

`support_grant.period_id`가 **NULL이면 연간 한도만**, 값이 있으면 **그 기간 한도만**
대신한다. 둘은 서로 독립이며 한 학생이 둘 다 가질 수 있고, 계산은 언제나
`min(기간 몫, 연간 몫)`을 따른다.

> 연간 한도만 300,000으로 낮추고 기간 한도(250,000)를 그대로 두면
> 1학기에 250,000, 2학기에 50,000을 쓰게 된다.
> 기간 한도까지 함께 줄이려면 기간 예외도 따로 넣어야 한다.

### 새 표 — `settlement_budget` (migration 003)

정산 시점의 학생별 지원금 상태(연간한도·기간한도·이월액·이전 사용액·가용액·
사용액)를 **스냅샷으로 저장한다.** 화면에서 다시 계산하지 않는 이유는,
정산 이후 정책이 바뀌면 저장된 배분액과 어긋난 숫자가 나란히 보이기 때문이다.
정산 결과는 그 자체로 완결된 기록이어야 한다.

### 낡음 판정에 더한 것

`prior_key`가 달라졌을 때 **어느 작업공간이 달라졌는지 찾아** 사람 말로 알린다.
그 작업공간이 이전 **지원기간**이면 이월액이 달라졌다는 뜻이므로 문구를 바꾼다.

| 상황 | 문구 |
|---|---|
| 같은 기간의 선행 작업공간 | 선행 작업공간(2026년 4월)의 정산이 변경되었습니다 |
| 이전 지원기간 | 선행 지원기간(1학기)의 정산이 변경되어 이월액이 달라졌습니다 |

### 학생 상세정보의 네 가지 상태

`해당없음`(자격 없음) · `정산 전`(정산 없음) · `재정산 필요`(낡음) · `최신`.
**`최신`일 때만 숫자를 준다.** 낡은 정산의 숫자를 최신처럼 보여 주지 않는 것이
이 칸의 목적이다.

## 18. Phase 4 구현 메모 (2026-09-06)

### 계층을 셋으로 나눴다 (요구사항 §14)

```
정산 엔진            domain/settle.rs      금액을 나눈다
  ↓ settlement / settlement_alloc / settlement_budget
행정자료 집계 서비스  repo/proposal.rs      부서 × 재원으로 모으고 이름표를 만든다
  ↓ Proposal 구조체
Excel writer         excel/admin.rs        받은 것을 파일에 쓴다 (계산 없음)
```

`excel/admin.rs`에는 덧셈이 없다. 학교 품의 양식이 바뀌면 이 파일만 고친다.
`repo/proposal.rs`도 원본 `charge`를 보지 않는다 — **최신 유효 정산만** 읽는다.

### 낡은 정산으로는 파일을 만들지 않는다

`repo::settle::require_fresh`가 관문이다. 정산이 없으면 `정산 전`, 낡았으면
`재정산 필요`로 막는다. **경고가 아니라 차단이다** — 잘못된 금액이 파일이 되어
학교 밖으로 나가면 되돌릴 수 없기 때문이다.

품의 미리보기와 Excel은 **같은 `build()` 결과**를 쓴다. 화면에서 본 금액과 파일의
금액이 다를 수 없다.

### 품의 열 이름표

`FUND_ORDER` 하나가 열 차례를 정하고(수익자 → 초과금 → 지원금 → 자유수강권),
이름표만 그 학년도의 대상학년에서 만든다.

| 재원 | 대상학년 `3` | 대상학년 `3,4` | 대상학년 없음 |
|---|---|---|---|
| SELF_PAY | 수익자(1,2,4,5,6학년) | 수익자(1,2,5,6학년) | 수익자 |
| VOUCHER_OVER | 3학년 초과금 | 3·4학년 초과금 | 이용권 초과금 |
| VOUCHER | 3학년 지원금 | 3·4학년 지원금 | 이용권 지원금 |
| FREE_VOUCHER | 자유수강권 | 자유수강권 | 자유수강권 |

`수익자(…)`의 학년 목록은 **전교생에 실제로 있는 학년**에서 대상학년을 뺀 것이다.
`support_policy.label_fund`/`label_over`에 직접 써 넣으면 그 값이 이긴다.

### 품의 분류는 `fund`만 본다 (요구사항 §8)

두 제도를 모두 가진 학생의 남은 금액은 `fund = VOUCHER_OVER`,
`origin = FREE_EXHAUSTED`다. 품의에서는 **`fund`를 따라 3학년 초과금**으로 간다.
`origin`은 수익자 탭의 내역 구분에만 쓴다. 이 규칙을
`중복_지원_학생은_fund를_기준으로_갈린다`로 못 박았다.

### 교차검증 — 같은 돈이 화면마다 달라지지 않는다

집계할 때마다 두 가지를 확인한다.

1. 부서마다 `네 열의 합 == 그 행의 합계`
2. 전체 `모든 부서 합계 == 그 항목의 정산 총액`

하나라도 어긋나면 `balanced = false`가 되고 Excel을 만들지 않는다.
테스트에서는 여기에 더해 **품의 ↔ 수익자 탭 ↔ 이용권 탭 ↔ 자유수강권 탭**의
합계가 서로 같은지도 본다.

### Excel

| 규칙 | 어떻게 |
|---|---|
| 금액은 숫자 셀 | `write_number_with_format` + `#,##0`. 문자열로 쓰면 Excel에서 합계가 안 된다 |
| 열 너비 | 열마다 따로 준다 — 이름 11, 부서 16, 금액 12, 학년·반·번호는 7 |

| 내부 코드 | 화면·파일 어디에도 `PLAIN` 같은 코드를 쓰지 않는다 |

### 화면 Excel은 필터를 따르지 않는다 (요구사항 §5)

[Excel 다운로드]는 **그 작업공간의 전체 정산 결과**를 내려받는다. 화면에 필터가

알려 준다. 검색어 때문에 학생이 빠진 자료가 학교 밖으로 나가면 안 되기 때문이다.

## 19. Phase 5 구현 메모 (2026-09-06)

자세한 절차는 [02-배포.md](02-배포.md)에 따로 적었다. 여기에는 **왜 그렇게 했는가**만 남긴다.

### 백업은 파일 복사가 아니다

SQLite는 WAL 방식이라 `.db`만 복사하면 `.db-wal`에만 있는 내용이 빠진다.
`rusqlite::backup` API를 쓰면 쓰는 도중에도 안전하고 나온 파일이 그 자체로
완결된다. `백업_파일은_그_자체로_열린다` 시험이 이것을 지킨다.

처음에는 마이그레이션 직전 백업만 `std::fs::copy`로 남겨 두었는데, 이것이
**가장 중요한 백업**(자료구조를 바꾸기 직전)이면서 유일하게 안전하지 않은
백업이었다. 파일을 떠 내는 코드를 `db::backup::dump_connection` 한 곳으로
모아, 백업을 만드는 다섯 군데가 모두 같은 방식과 같은 이름 규칙을 쓴다.

### 시험이 잡은 버그 — 같은 초의 백업 덮어쓰기

파일 이름이 초 단위(`…-173000.db`)라 같은 초에 두 번 만들면 앞의 것이
덮어써졌다. 사람이 [백업]을 빠르게 두 번 누르거나, 삭제 직전 백업과 복원 직전
백업이 같은 초에 겹칠 수 있다. **백업을 덮어쓰는 것은 백업이 없는 것보다
나쁘다** — 이름이 겹치면 `-2`를 붙이도록 고쳤다.

### 복원은 실패해도 자료를 잃지 않는 순서로

```
검사 → 안전백업 → 갈아 끼움 → 마이그레이션
```

검사에서 걸리면 갈아 끼우기를 아예 시작하지 않으므로 현재 자료가 멀쩡하다.
갈아 끼운 뒤에 실패하면 안전백업으로 되돌린다. 되돌리기까지 실패하면 사람에게
파일 이름을 알려 준다 — 프로그램이 못 하는 일을 사람이 할 수 있게 두는 것이
아무 말 없이 끝내는 것보다 낫다.

`Db`가 `Mutex<Connection>` 하나를 들고 있으므로, 갈아 끼울 때 잠시 메모리 연결로
바꿔 두어 기존 연결을 닫고 파일을 푼다.

### 자동백업의 두 갈래

| 실패하면 | 시점 | 왜 |
|---|---|---|
| **진행** | 앱 시작, 마이그레이션 직전 | 백업을 못 만든 것 때문에 업무를 못 하면 더 손해다 |
| **중단** | 복원 직전, 전체 삭제 직전 | 되돌릴 방법이 없는 채로 자료를 지울 수 없다 |

보존 개수는 종류마다 10개이고, **사람이 만든 백업과 안전백업은 지우지 않는다.**

### 구버전 백업은 올려서 복원, 신버전은 막는다

`user_version`이 낮으면 복원 뒤 마이그레이션을 차례로 적용한다. 높으면 막는다 —
우리가 모르는 표와 컬럼을 다룰 수 없다. `구버전_백업은_자료구조를_올려_복원한다`와
`현재보다_새로운_백업은_막는다`가 양쪽을 지킨다.

### 배포 설정을 코드가 아니라 시험으로 지킨다

과거에 겪은 문제 — `latest.json` 누락, updater artifact 누락, 서명 불일치,
세 곳의 버전 불일치 — 는 **빌드 전에 설정 파일만 봐도 알 수 있는 것**이다.
그래서 `version_tests.rs`가 설정을 읽어 검사한다.

| 시험 | 막는 문제 |
|---|---|
| `버전이_세_곳에서_같다` | updater가 새 버전을 알아보지 못함 |
| `updater_설정이_빠지지_않았다` | 확인 주소·공개키 누락 |
| `updater_배포물을_만들도록_되어_있다` | `.sig` 누락 → "설치는 됐지만 업데이트 실패" |
| `윈도우_설치파일_설정이_있다` | 설치파일이 안 나옴, 관리자 권한 요구 |
| `자료_폴더_식별자가_바뀌지_않았다` | 기존 사용자의 자료를 못 찾음 |
| `한글_이름_설치파일을_영문으로_바꿔_올린다` | 첨부 파일 주소와 `latest.json`이 어긋남 |
| `저장소_주소가_세_곳에서_같다` | 한 곳만 고쳐 업데이트 확인이 조용히 실패 |
| `옛_저장소_이름이_남아_있지_않다` | 임시 주소가 남아 없는 곳을 봄 |
| `릴리스_첨부_파일_이름이_약속과_같다` | 파일 이름 규칙이 바뀌어 주소가 어긋남 |

CI 워크플로도 빌드 전에 이 시험을 먼저 돌린다.

### 첫 실제 빌드가 잡아낸 것 두 가지

설정만 보는 시험으로는 못 잡고 **실제로 빌드해 봐야 드러나는** 문제였다.

1. **`.sig`가 조용히 빠졌다.** 서명 키 환경변수 이름을 `TAURI_SIGNING_PRIVATE_KEY_PATH`로
   주었는데 Tauri 2에는 그런 변수가 없다. 설치파일은 정상으로 나오고 종료 코드도
   0이며, 로그 맨 끝 한 줄에만
   `A public key has been found, but no private key`가 남는다.
   **빌드가 성공했다는 것만으로 배포물이 온전하다고 볼 수 없다**는 예다.
   그래서 워크플로가 `.sig`가 없으면 릴리스를 만들지 않고 멈춘다.

2. **설치파일 이름이 한글이었다.** 앱 이름이 한글이라 makensis 결과물도
   `방과후 통합 매니저_0.1.0_x64-setup.exe`다. GitHub Release는 첨부 파일 이름에서
   한글을 떼어 내므로 `latest.json`의 `url`과 실제 주소가 어긋나 업데이트가
   "받는 중"에서 실패한다. 그래서 tauri-action의 `includeUpdaterJson`을 버리고,
   빌드 뒤 **영문 이름으로 복사한 다음 `latest.json`을 직접 만든다.**
   앱과 시작 메뉴에 보이는 이름은 그대로 한글이다.

### 업데이트는 사람이 누를 때만

앱을 켤 때 자동으로 확인하지 않는다. 확인 실패가 앱 실행을 막지도 않는다 —
학교 방화벽에 걸려 업무를 못 하게 되면 안 된다. 동의 없이 설치하지 않는다.

### 다시 시작 버튼을 두지 않는다

Windows에서 `install()`은 **돌아오지 않는다.** 플러그인이 설치 프로그램을
`/P /UPDATE /R`로 띄운 뒤 앱을 스스로 끝내고, 설치가 끝나면 NSIS가 앱을 다시
켠다. 여기서 화면이 `relaunch()`를 부르면 방금 뜬 설치 프로그램과 경쟁해서,
앱이 먼저 켜지는 바람에 파일을 바꾸지 못하고 **구 버전 그대로 남는다.**
겉으로는 "업데이트했는데 그대로"로 보이는 가장 고약한 실패다.

그래서 [지금 다시 시작] 버튼을 없애고 `process` 플러그인과 그 권한
(`process:allow-restart`)까지 걷어냈다. 쓰지 않는 권한을 남겨 두면 나중에
누군가 다시 부르게 된다.

### 로그에 개인정보를 남기지 않는다

건수와 파일 이름만 남긴다. 학생 이름이나 금액은 적지 않는다.
사용자가 오류를 알려 줄 때 로그 파일을 그대로 보내도 안전해야 하기 때문이다.

### 저장소 이름은 확정된 값 하나만 남긴다 (2026-09-06)

## 20. 반은 문자다 (2026-09-07, 최종 QA)

실제 학교 자료를 넣어 보다 나온 것이다. 우리 학교는 반을 `1 2 3`이 아니라
`가 나 다`로 쓴다. `class_no`가 `INTEGER CHECK (1~99)`였으니 이런 학교는
프로그램을 아예 쓸 수 없었다.

### 왜 표를 다시 만들었나

SQLite는 컬럼 타입을 못 바꾼다. 게다가 INTEGER 자리에 `'1'`을 넣으면 타입
친화성 때문에 숫자 1로 되돌아가서, 숫자와 문자가 섞인 자료가 된다. 그러면
`class_no = '1'`로 찾을 때 안 잡히는 학생이 생긴다 — 학생 매칭이 조용히
어긋나는 가장 나쁜 종류의 버그다. 그래서 SQLite 공식 절차대로 갈아 끼웠다.

### 외래키를 끄지 않으면 수강 자료가 날아간다

`enrollment` · `support_eligibility` · `support_grant`가 `student(id)`를
**`ON DELETE CASCADE`**로 참조한다. 외래키를 켠 채 `DROP TABLE student`를 하면
SQLite가 먼저 모든 행을 지우고 그 연쇄로 수강 자료까지 사라진다.

`PRAGMA foreign_keys`는 트랜잭션 안에서 듣지 않으므로, 마이그레이션 러너에
`fk_off` 표시를 두어 **트랜잭션 바깥에서** 껐다 켠다. 대신 **커밋하기 전에**
`foreign_key_check`를 돌려, 어긋나면 아무것도 적용되지 않고 되돌아간다.
커밋한 뒤에 검사하면 찾아도 되돌릴 수 없다.

### 정렬 — 숫자 학교의 쓰임새를 지킨다

문자로 바꾸고 사전순으로 놓으면 `1, 10, 2, 3`이 된다. 그래서 정렬용 열쇠를
만든다.

```text
숫자 반  '1'  → "0000001"     '10' → "0000010"
문자 반  '가' → "1가"
```

앞자리 `0`/`1` 덕분에 숫자 반이 늘 문자 반보다 앞에 오고, 숫자끼리는 자연
정렬, 문자끼리는 유니코드 차례(=한글 차례)가 된다. 어떤 차례로 넣어도 결과가
같다.

같은 규칙이 **세 곳**에 있다.

| 곳 | 무엇 |
|---|---|
| `student.class_sort` | GENERATED 열. SQL `ORDER BY`가 쓴다 |
| `domain::class_no::sort_key` | Rust 안에서 줄 세울 때 |
| `format.ts` `classSortKey` | 화면에서 열 제목을 눌러 정렬할 때 |

세 곳이 어긋나면 화면과 엑셀의 차례가 달라진다. 그래서
`DB_정렬_열쇠가_domain_규칙과_같다` 시험이 DB가 만든 값과 Rust가 만든 값을
학생마다 맞대어 본다.

### 앞뒤 공백을 떼는 까닭

엑셀에서 온 `'1 '`과 손으로 친 `'1'`이 서로 다른 반이 되면, 같은 학생이 둘로
갈라지고 매칭이 어긋난다. 그래서 저장할 때 `trim`하고, DB에도
`class_no = trim(class_no)` 제약을 걸었다. 가운데 글자는 손대지 않는다 —
학교가 쓰는 이름을 프로그램이 고쳐서는 안 된다.

### 기존 사용자에게 뜻이 바뀌지 않는다

숫자 1은 문자 `'1'`이 된다. 화면·엑셀·품의에 보이는 것은 그대로다.
학생 `id`를 그대로 옮기므로 수강·지원대상자·정산과의 연결도 끊기지 않는다.
`user_version`만 3 → 4가 되므로 **업데이트만으로 정산이 낡음이 되지도 않는다.**

실제 사용 중인 자료 사본으로 확인했다 — 15개 표의 건수가 하나도 줄지 않았고,
반 `1`이 `'1'`(typeof=text)로 옮겨졌다.

### 반만 바꿔도 다시 정산하라고 하지 않는다

`yr_bump_student_grade` 트리거는 표를 지울 때 함께 사라지므로 004가 다시
만든다. 예전과 같이 **학년이 바뀔 때만** 올린다. 반은 금액에 영향이 없으므로
올리지 않는다 — 뜻 없는 경고가 자꾸 뜨면 사람이 경고를 무시하게 된다.

## 21. 학생 상세정보 조회 범위 (2026-09-07, 최종 QA)

전교생을 넣어 보니 한 학년이 100명을 넘었다. 학년만 고르면 그 100명을 한
화면에 다 그려서 쓸 수 없었다. **구조는 그대로 두고 조회 범위만 손봤다** —
검색 결과에서 학생을 고르면 아래에 상세정보가 열리는 방식은 유지한다.

### 학년만 고른 경우는 아예 찾지 않는다

빈 목록을 보여 주는 것과 다르다. 무엇을 더 넣어야 하는지 알려 준다.

> 검색 범위가 넓습니다. 반을 선택하거나 번호·이름을 입력해주세요.

**이 경우만 막는다.** 반·번호·이름 가운데 하나라도 있으면 범위가 충분히
좁혀지고, 그래도 많이 나오면 [더 보기]가 받아 준다. 번호나 이름만으로
학년을 넘어 찾는 기존 동작도 그대로다.

### 20명씩 보여 준다

```
27명 검색됨 · 20명 표시 중
[7명 더 보기]        → 누르면 →      27명 검색됨
```

남은 인원을 숫자로 적는다. `[더 보기]`만 있으면 몇 번 더 눌러야 하는지
알 수 없다.

조건을 바꾸거나 [초기화]를 누르면 **펼쳐 둔 상태도 함께 되돌린다.** 앞 검색에서
40명까지 펼쳐 둔 채 새 검색을 하면 갑자기 40명이 쏟아진다.

### 규칙을 화면에서 떼어 냈다

`lib/studentSearch.ts`에 순수 함수로 두었다 — 조건이 있는가, 너무 넓은가,
AND 로 거르고 정렬하기, 표시 문구와 남은 인원. 화면은 그 결과를 그리기만 한다.

그래야 시험할 수 있다. 이 규칙은 화면을 띄우지 않고도 틀린 것을 잡을 수 있는
종류인데, 그동안 이 프로젝트에는 화면 쪽 시험 도구가 없었다. **vitest 를
넣었다** (`npm run check` 가 함께 돌린다). 정렬은 `학년 → 반 자연정렬 →
번호 → 이름`으로, 20장에서 정한 반 규칙을 그대로 쓴다.

DB 와 정산에는 손대지 않았다. 마이그레이션도 없다.

## 22. 취소해도 이미 발생한 비용은 징수한다 (2026-09-07, 최종 QA)

실제 업무 자료를 넣어 보다 나온 것이다. **수강취소 = 수강료 전체 0원이 아니다.**
중도에 그만두어도 교재비·재료비는 배부한 뒤라면 환불하지 않고, 강사료·수용비는
실제 수강한 만큼 받는다.

그런데 정산 엔진에 자료를 넣는 SQL이 `WHERE e.status = 'ACTIVE'` 였다. 취소하면
그 학생의 징수금액 전체가 정산에서 사라졌다.

### 상태와 금액을 나눈다

`Enrollment.status` 는 **지금 수강 중인가**만 뜻한다. 정산 대상은 **charge 금액**이
정한다.

```text
ACTIVE    + 금액 있음  → 정산
CANCELLED + 금액 있음  → 정산   ← 예전에는 여기가 빠졌다
CANCELLED + 전액 0원   → 정산할 것이 없음
```

정산 엔진(`domain::settle`)은 원래부터 `status` 를 모른다 — 고칠 것이 하나도
없었다. 잘못은 엔진에 자료를 넣어 주는 쪽에만 있었다.

`repo::settle::SETTLE_TARGET` 한 곳에 이 정의를 두고, 검증·자격자 수·대상학년
경고·우선순위 목록이 모두 그것을 쓴다.

### `ACTIVE` 를 일괄 제거하지 않았다

"정산에 넣을 금액"과 "수강 중인 인원"은 다른 질문이다. 그래서 아래는 그대로 뒀다.

| 그대로 둔 곳 | 까닭 |
|---|---|
| 부서 수강인원, 학년도 수강인원 | 실제 수강 중인 사람 수 |
| 중복 활성 수강 방지 (부분 유니크 인덱스) | 취소 후 재등록을 허용하는 장치 |
| 수강생 명단의 합계 줄 | 수강 중 금액을 보여 주는 자리 |

### 취소할 때 최종 징수금액을 함께 받는다

기본값은 **지금 금액 그대로**다. 0을 기본값으로 하면 환불하지 않는 교재비를 매번
다시 입력해야 한다. 프로그램은 강사료·수용비를 자동 계산하지 않는다 — 실제 수강한
만큼이 얼마인지는 담당자만 안다. [전액 징수]·[전액 면제] 두 버튼으로 흔한 두 경우를
한 번에 처리한다.

금액·상태·이력은 **한 트랜잭션**이다(`Db::write` 가 감싼다). 따로 하면 "취소는
됐는데 금액은 그대로"가 남는다.

### 복원해도 금액을 되돌리지 않는다

취소할 때 담당자가 확정한 금액을 그대로 둔다. 프로그램이 임의로 부서 기준금액으로
바꾸면 그 판단이 조용히 사라진다. 다시 받아야 한다면 사람이
[부서 기준금액으로 되돌리기]를 고른다. 부서 기준금액을 고쳐도 학생 금액을 자동으로
바꾸지 않는 기존 원칙과 같은 결이다.

### 이력은 한 줄

한 번의 취소를 `ENROLL_CANCEL` 한 건으로 남긴다.

```
이전: 수강중 · 강사료 30,000 · … · 합계 58,000
변경: 취소   · 강사료 15,000 · … · 합계 41,500
사유: 5월 중도 포기, 교재·재료 배부 완료
```

두 줄로 쪼개면 "왜 금액이 줄었나"를 두 줄을 맞춰 봐야 알 수 있다.

### 예전 취소 자료는 추측하지 않는다

예전 버전에서 취소한 건은 금액이 취소 전 그대로다. 그것이 이제 정산에 들어가므로,
0원으로 만들면 징수할 돈을 놓치고 전액으로 두면 안 받을 돈을 받는다. 그래서
**정산 생성 전 검사에서 사람에게 확인시킨다** (`CANCEL_FULL_AMOUNT` WARN).
migration 은 없다.

### stale 은 이미 자동이다

`ws_bump_enr_u`(상태 변경)와 `ws_bump_chg_u`(금액 변경) 트리거가 이미
`workspace.data_version` 을 올린다. 취소하면 정산이 곧바로 재정산 필요가 된다.
새 트리거는 필요 없었다.

## 23. 행정자료 › 학생별 징수 내역 (2026-09-07, 최종 QA)

작업공간에서 **학생별로 실제 징수해야 할 수강료**를 확인하고 Excel로 받는 자료다.

### 자료 원천은 정산이 아니다

`Enrollment + Charge` 만 본다. 지원금 배분 결과(`settlement_alloc`)는 쓰지 않는다.
그래서 **정산이 없거나 재정산 필요 상태여도 조회·내려받기가 된다** — 정산 *전에*
금액을 대조하는 자료이기 때문이다. 이 점이 수익자·이용권·자유수강권 화면과 다르다
(그쪽은 정산이 최신일 때만 낸다).

새 SQL도 새 표도 필요 없었다. `repo::enrollment::list` 가 이미 학년·반·번호·이름·
지원유형·부서·항목별 금액·합계·상태를 다 준다. 걸러 내는 규칙도 `EnrollmentFilter`
그대로 쓴다 — 두 곳이 달라지면 안 된다. 차례만 다르다.

| | 차례 |
|---|---|
| 수강생 명단 | 부서 우선 (부서별로 일하는 화면) |
| 학생별 징수 내역 | **학생 우선** — `학년 → 반 자연정렬 → 번호 → 이름 → 부서` |

### 취소자는 사라지지 않는다

취소할 때 확정한 징수금액을 그대로 보여 주고 상태를 `수강취소` 로 적는다.
합계 0원인 취소자도 **화면과 Excel 모두에 남긴다** — 정산에서는 빠지지만
"이 학생을 전액 면제로 처리했다"는 사실을 확인할 자리가 필요하다.

### Excel 은 화면 필터를 반영한다

행정자료 가운데 이것만 필터를 반영한다.

| 종류 | 필터 | 정산 최신 요구 |
|---|---|---|
| 수익자·이용권·자유수강권·품의 | 무시(전체) | 요구 |
| **학생별 징수 내역** | **반영** | 요구하지 않음 |

수익자 쪽이 전체만 내는 까닭은 학교 밖으로 나가는 문서라 일부만 담긴 파일이
만들어지면 안 되기 때문이다. 이 자료는 다르다 — "2학년만 뽑아 담임에게 확인"
하는 식으로 쓴다.

대신 전체로 오해하지 않게 조건을 두 곳에 적는다.

* 파일 이름 — `학생별징수내역_2026학년도_4월_2학년·나리반_20260907.xlsx`
* **맨 아래 합계 줄** — 조건 · 학생 수 · 수강 건수 · 항목별 합계 · 총액

조건을 시트 **맨 위**에 얹지 않았다. 그러면 헤더가 한 줄 밀려서 이 파일을 다시
읽는 도구가 열을 찾지 못한다 (`read_first_sheet` 는 첫 줄을 헤더로 본다).
업로드 검증과 공용인 리더를 이 자료 하나 때문에 고칠 수는 없다.

### 요약의 학생 수는 행 수가 아니다

한 학생이 세 부서를 수강하면 행은 3개지만 학생은 1명이다. `student_id` 를 모아
중복을 뺀다.

### 읽기 전용

금액 수정은 수강생 명단에서 한다. 같은 금액을 두 화면에서 고칠 수 있으면
어느 쪽이 최신인지 헷갈린다.
