# 배포 · 백업 · 업데이트 (Phase 5)

## 0. 확정된 값

| 항목 | 값 |
|---|---|
| GitHub 저장소 | **`lohemal/AfterSchool-Total-Manager`** |
| Release 태그 | `v0.1.0`, `v0.1.1`, … (`v` + 앱 버전) |
| 첨부 파일 | `afterschool_<버전>_x64-setup.exe` · `.exe.sig` · `latest.json` · `SHA256SUMS.txt` |
| 앱 표시명 | 방과후 통합 매니저 (한글 그대로) |
| 자료 폴더 식별자 | `kr.school.afterschool` (바꾸면 기존 자료를 못 찾는다) |

저장소 주소가 나오는 곳은 **세 곳**이다. 하나만 고치면 업데이트 확인이 조용히
실패하므로 시험으로 묶어 두었다(`저장소_주소가_세_곳에서_같다`).

| 위치 | 무엇 |
|---|---|
| `tauri.conf.json` → `plugins.updater.endpoints[0]` | `latest.json`을 읽는 주소 |
| `tauri.conf.json` → `bundle.homepage` | 설치 정보에 보이는 주소 |
| `src-tauri/src/commands/system.rs` → `RELEASE_URL` | [Release 페이지 열기] |

워크플로는 주소를 적어 두지 않고 `${{ github.repository }}`로 받는다 — 저장소
안에서 돌기 때문에 따로 고칠 곳이 없다.

## 1. 자료가 어디에 있는가

```
%APPDATA%\kr.school.afterschool\
  afterschool.db          업무 자료 (SQLite)
  afterschool.db-wal      쓰기 중 임시 파일
  afterschool.db-shm
  backups\                백업 파일
  exports\                Excel 출력
  logs\                   로그 (30일 보관)
```

프로그램은 `%LOCALAPPDATA%\방과후 통합 매니저\`에 설치된다(NSIS `currentUser`,
관리자 권한 불필요). **두 폴더는 완전히 떨어져 있다** — 프로그램을 업데이트하거나
지우고 다시 설치해도 자료 폴더는 손대지 않는다.

이 경로는 `tauri.conf.json`의 `identifier`(`kr.school.afterschool`)에서 나온다.
그래서 identifier를 바꾸면 기존 자료를 못 찾는다. 시험으로 못 박아 두었다
(`자료_폴더_식별자가_바뀌지_않았다`).

## 2. 백업 구조

### 파일 복사를 쓰지 않는다

SQLite는 WAL 방식이라 `.db`만 복사하면 아직 `.db-wal`에만 있는 내용이 빠진다.
그래서 **SQLite 백업 API**(`rusqlite::backup`)를 쓴다. 쓰는 도중에도 안전하고,
나온 파일은 그 자체로 완결된다. 시험으로 확인한다
(`백업_파일은_그_자체로_열린다`).

백업을 만드는 곳은 다섯 군데(아래 표)지만 실제로 파일을 떠 내는 코드는
`db::backup::dump_connection` **하나뿐이다.** 마이그레이션 직전 백업도 이 함수를
쓴다 — 가장 중요한 백업이 파일 복사로 남는 일이 없어야 하기 때문이다.
이름이 겹치지 않게 번호를 붙이는 규칙도 여기 한 곳에만 있다.

### 종류

파일 이름 앞머리로 구분한다.

| 이름 | 언제 | 자동 정리 |
|---|---|---|
| `afterschool-backup-…` | 사람이 [지금 백업]을 눌렀을 때 | **안 함** |
| `auto-startup-…` | 앱을 켤 때 | 최근 10개 |
| `before-delete-…` | 전체 삭제 직전 | 최근 10개 |
| `before-restore-…` | 복원 직전 | **안 함** |
| `before-migrate-v<N>-…` | 자료구조 갱신 직전 | **안 함** |

`afterschool-backup-20260906-173000.db` 처럼 날짜와 시각이 들어간다.
같은 초에 두 번 만들면 `…-173000-2.db`로 번호가 붙는다 — 백업을 덮어쓰는 것은
백업이 없는 것보다 나쁘기 때문이다(시험이 이 버그를 잡아냈다).

**사람이 만든 백업과 안전백업은 개수 제한이 없다.** 지우려면 화면에서 직접
[삭제]를 누른다.

## 3. 복원 구조

```
1. 고른 파일 검사        ← 여기서 걸리면 현재 자료를 건드리지 않는다
2. 지금 자료를 안전백업
3. 연결을 닫고 갈아 끼움
4. 열면서 마이그레이션
```

3·4에서 어긋나면 2의 안전백업으로 되돌린다. 되돌리기까지 실패하면 화면에
안전백업 파일 이름을 알려 주고 사람이 직접 바꿔 끼울 수 있게 한다.

### 1단계에서 무엇을 보는가

| 검사 | 걸리면 |
|---|---|
| 파일이 있는가 | `선택한 파일을 찾지 못했습니다.` |
| 열리는 SQLite인가 | `SQLite 자료 파일이 아닙니다.` |
| `PRAGMA quick_check` | `파일이 손상되어 읽을 수 없습니다.` |
| 핵심 표 6개가 있는가 | `이 프로그램의 백업 파일이 아닙니다.` |
| `user_version`이 0이 아닌가 | `자료구조 버전을 읽을 수 없는 파일입니다.` |
| `user_version` ≤ 현재 | `이 백업파일은 현재 프로그램보다 새로운 버전에서 생성되었습니다. 프로그램을 업데이트한 후 다시 시도해주세요.` |

핵심 표는 `academic_year · workspace · student · department · enrollment · charge`.

### 구버전 백업

`user_version`이 현재보다 **낮으면** 복원한 뒤 마이그레이션을 차례대로 적용해
현재 버전까지 올린다. 화면에는 `자료구조를 1 → 3으로 올렸습니다`로 알린다.
**높으면 막는다** — 우리가 모르는 표와 컬럼을 다룰 수 없기 때문이다.

## 4. 자동백업 정책

| 시점 | 종류 | 실패하면 |
|---|---|---|
| 앱 시작 | `auto-startup` | 로그만 남기고 **앱은 계속 뜬다** |
| 마이그레이션 직전 | `before-migrate` | 로그만 남기고 갱신은 진행 |
| 복원 직전 | `before-restore` | 복원을 중단 (백업 없이 복원하지 않는다) |
| 전체 삭제 직전 | `before-delete` | 삭제를 중단 |

앞의 둘은 실패해도 진행한다 — 백업을 못 만든 것 때문에 업무를 못 하면 더 손해다.
뒤의 둘은 실패하면 멈춘다 — 되돌릴 방법이 없는 채로 자료를 지울 수 없다.

전체 삭제 화면은 무엇이 사라지는지 건수까지 적어 보여 준다. 예:

> 이 작업은 **2026년 4월** 작업공간의 수강 자료 **37건**을 모두 삭제합니다.
> 취소 상태인 수강까지 함께 사라지고 …
> 삭제 직전에 **자동으로 백업**됩니다.

## 5. updater 구조

Tauri 공식 updater 플러그인을 쓴다.

```
[업데이트 확인]  → check()             GitHub의 latest.json 을 읽는다
새 버전 안내     → 사람이 [내려받아 설치]
내려받기         → update.download()   진행률 표시
설치             → update.install()    여기서 앱이 스스로 닫힌다
다시 시작        → NSIS가 알아서 켠다
```

### `relaunch()`를 부르면 안 된다

Windows에서 `install()`은 **돌아오지 않는다.** 플러그인이 설치 프로그램을
`/P /UPDATE /R`로 띄운 뒤 `std::process::exit(0)`으로 앱을 스스로 끝내고,
설치가 끝나면 NSIS가 `/R` 때문에 앱을 다시 켠다.

그래서 화면에서 따로 `relaunch()`를 부르면 **방금 뜬 설치 프로그램과 경쟁한다.**
앱이 먼저 다시 켜지면 NSIS가 실행 중인 파일을 바꾸지 못하고 포기하므로,
겉으로는 "업데이트했는데 그대로"가 된다. 그래서 [다시 시작] 버튼을 두지 않고,
`process` 플러그인 자체를 넣지 않았다(쓰지 않는 권한을 두지 않는다).

### 한 번에 끝나야 한다

`check()`가 돌려준 `Update` 객체 하나로 설치까지 간다. 앱을 다시 켠 뒤 처음부터
다시 확인해야 하는 구조가 되면 안 된다.

- **앱을 켤 때 자동으로 확인하지 않는다.** 사람이 누를 때만 확인한다.
  자동 확인을 넣고 싶으면 `app_setting`에 마지막 확인 시각을 두고 24시간이
  지났을 때만 부르면 된다(구조는 준비되어 있고 기본은 꺼져 있다).
- **동의 없이 설치하지 않는다.** 확인 → 안내 → 사람이 고름 → 설치 → 사람이 재시작.
- **확인 실패가 앱을 막지 않는다.** 인터넷이 없거나 학교 방화벽에 걸리면
  업데이트 칸에만 안내가 뜨고 나머지 기능은 그대로 쓴다.
- 저장소 주소는 앱 안에 박혀 있고 사용자가 입력하지 않는다(§0의 세 곳).
  화면에는 URL을 노출하지 않고 [Release 페이지 열기] 버튼만 둔다.

### 서명 키

```
%USERPROFILE%\.afterschool-release\afterschool.key       개인 키 (절대 커밋 금지)
%USERPROFILE%\.afterschool-release\afterschool.key.pub   공개 키
```

공개 키는 `tauri.conf.json`의 `plugins.updater.pubkey`에 박혀 있다. 앱은 이 키로
서명을 확인하므로, **개인 키를 잃으면 더 이상 업데이트를 낼 수 없다.**
안전한 곳에 따로 보관해 두어야 한다.

CI에 등록할 Secret은 **하나뿐이다.**

| Secret | 값 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `afterschool.key` 파일 내용 전체 |

### 비밀번호 Secret은 등록하지 않는다

키에 비밀번호를 걸지 않았는데, GitHub은 **빈 값 Secret을 저장할 수 없다.**
그래서 등록하지 않고 워크플로가 직접 빈 문자열을 넘긴다.

```yaml
TAURI_SIGNING_PRIVATE_KEY_PASSWORD="" npm run app:build
```

이걸 빼면 안 된다. 서명 키는 비밀번호를 걸지 않았어도 **scrypt로 감싸여
있어서**(`kdf_alg = "Sc"`) 복호화에 비밀번호가 필요하고, 빈 문자열이 그
비밀번호다. 환경변수가 아예 없으면 tauri가

```
Info Decrypting updater signing key, expect a prompt for password
```

를 찍고 입력을 기다린다. **설치파일은 멀쩡히 나오는데 `.sig`만 빠진다.**

`env:` 블록에 `""`로 적어서도 안 된다 — Windows에서는 빈 값 환경변수가
"없는 변수"로 사라질 수 있어 같은 멈춤으로 되돌아간다. bash 한 줄 대입이라야
확실하다. 시험으로 못 박아 두었다(`서명_비밀번호를_빈_문자열로_넘긴다`).

나중에 비밀번호 있는 키로 바꾸면 그 자리에
`${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}`를 넣고 Secret을 등록한다.

### 환경변수 이름

**`TAURI_SIGNING_PRIVATE_KEY`** 하나뿐이다. `..._PATH` 같은 변수는 Tauri 2에
없다 — 이름을 틀리면 설치파일은 나오지만 `.sig`가 조용히 빠지고, 로그 맨
끝에만 `A public key has been found, but no private key`가 남는다.

```bash
TAURI_SIGNING_PRIVATE_KEY="$(cat "$USERPROFILE/.afterschool-release/afterschool.key")" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD="" \
npm run app:build
```

## 6. GitHub Release에 반드시 있어야 하는 파일

하나라도 빠지면 "설치는 됐지만 업데이트 실패"가 된다.

| 파일 | 없으면 |
|---|---|
| `afterschool_<버전>_x64-setup.exe` | 내려받을 것이 없다 |
| `afterschool_<버전>_x64-setup.exe.sig` | 서명 확인 실패 |
| `latest.json` | 새 버전이 있는지 알 수 없다 (확인 자체가 실패) |
| `SHA256SUMS.txt` | (없어도 업데이트는 된다. 직접 받은 파일 검증용) |

### 파일 이름을 영문으로 바꿔 올리는 이유

앱 이름이 한글이라 makensis가 만드는 파일도 한글 이름이다
(`방과후 통합 매니저_0.1.0_x64-setup.exe`). 그런데 **GitHub Release는 첨부 파일
이름에서 한글을 떼어 낸다** — `_0.1.0_x64-setup.exe`가 되어 버린다.
그러면 `latest.json`의 `url`과 실제 첨부 파일 주소가 어긋나 업데이트가
"받는 중"에서 실패한다.

그래서 워크플로가 빌드 뒤에 **영문 이름으로 복사한 다음 `latest.json`을 직접
만든다.** tauri-action의 `includeUpdaterJson`은 쓰지 않는다(한글 이름을 그대로
가리키기 때문이다). 앱 화면과 시작 메뉴에 보이는 이름은 그대로 한글이다.

`tauri.conf.json`의 `bundle.createUpdaterArtifacts: true`가 `.sig`를 만든다.
서명이 없으면 워크플로가 릴리스를 만들지 않고 멈춘다.
이 두 가지 모두 시험으로 못 박아 두었다
(`updater_배포물을_만들도록_되어_있다`, `한글_이름_설치파일을_영문으로_바꿔_올린다`).

`latest.json`은 이런 모양이다.

```json
{
  "version": "0.1.1",
  "notes": "...",
  "pub_date": "2026-09-06T…Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "…",
      "url": "https://github.com/lohemal/AfterSchool-Total-Manager/releases/download/v0.1.1/afterschool_0.1.1_x64-setup.exe"
    }
  }
}
```

`version`이 앱의 현재 버전보다 클 때만 새 버전으로 본다. 그래서 세 곳의 버전이
어긋나면 업데이트가 오작동한다.

### 발행 직후에는 값이 한동안 흔들린다

`releases/latest/download/latest.json`은 CDN을 타므로, 릴리스를 발행하는 순간에는
엣지마다 새 버전과 옛 버전이 갈려 보인다. 실제로 v0.1.1을 낼 때 발행 시각보다
앞서 `0.1.1`이 읽힌 적이 있고, 곧이어 같은 주소가 다시 `0.1.0`을 돌려주었다.

그래서 **릴리스가 끝났는지는 `latest.json` 한 번 읽어서 판단하면 안 된다.**
첨부 파일 네 개가 실제로 붙었는지를 봐야 한다. 사용자에게 미치는 영향은 없다 —
발행 직후 몇 분 안에 [업데이트 확인]을 누른 사람이 한 번 더 눌러야 할 수 있을
뿐이다.

## 7. 저장소 만들기와 첫 Release

### ① 저장소 만들고 밀어 넣기

이 PC의 git 자격 증명이 다른 계정이라 원격 주소에 `lohemal@`을 붙인다
(보결 배정 시스템과 같다).

```bash
git remote add origin https://lohemal@github.com/lohemal/AfterSchool-Total-Manager.git
git push -u origin main
```

### ② 서명 키를 Secrets에 넣기

저장소 → Settings → Secrets and variables → Actions → New repository secret.

| Secret | 값 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `%USERPROFILE%\.afterschool-release\afterschool.key` 파일 내용 **전체** |

**이것 하나뿐이다.** 비밀번호 Secret은 등록하지 않는다(§5 참고).

키를 빠뜨리면 워크플로가 빌드를 시작하기 전에 멈추고, 서명이 안 되면
릴리스를 만들지 않고 멈춘다. 어느 쪽이든 Actions가 빨간불로 알려 준다.

### ③ 첫 Release

```bash
git tag v0.1.0
git push origin v0.1.0
```

Actions가 검사 → 빌드 → 서명 → 이름 정리 → `latest.json` 생성 → Release 발행을
한다. 끝나면 Release 페이지에 파일 네 개가 있어야 한다(§6).

### ④ 다음 버전부터

```bash
npm run version:set 0.1.1     # package.json · tauri.conf.json · Cargo.toml 한꺼번에
npm run check                 # 버전 일치 + 저장소 주소 + 전체 테스트
git commit -am "v0.1.1"
git tag v0.1.1
git push origin main --tags
```

태그는 `v` + 앱 버전이다(앱 `0.1.1` → 태그 `v0.1.1`).
버전이 어긋나면 `npm run check`가 먼저 막는다.

## 9. Windows SmartScreen

**코드로 없앨 수 없다.** 정직하게 구분하면 이렇다.

| 할 수 있는 것 | 방법 |
|---|---|
| 설치 자체를 쉽게 | `currentUser` 설치라 관리자 권한을 묻지 않는다 |
| 발행자 이름 표시 | `bundle.publisher` — 서명이 없으면 "알 수 없는 발행자"로 보인다 |

| 코드서명이 필요한 것 | 설명 |
|---|---|
| SmartScreen 경고 없애기 | OV/EV 코드서명 인증서가 있어야 한다. 연 20~50만 원 수준 |
| 즉시 신뢰 | EV 인증서만 즉시. OV는 배포량이 쌓이며 평판이 생겨야 한다 |

지금은 인증서가 없으므로 처음 실행할 때
`Windows가 PC를 보호했습니다` → [추가 정보] → [실행]을 눌러야 한다.
학교에 배포할 때 이 안내를 함께 주는 것이 현실적이다.

인증서를 나중에 넣을 수 있게 구조는 막아 두지 않았다 —
`tauri.conf.json`의 `bundle.windows`에 `certificateThumbprint`를 더하고 CI에
인증서를 넣으면 된다. 지금은 그 항목이 없을 뿐이다.

## 10. 앱 아이콘

2026-09-06에 정식 아이콘으로 교체했다. 원본은 `src-tauri/icons/source.png`
하나이고, 나머지는 모두 여기서 만들어진다.

```bash
npx tauri icon src-tauri/icons/source.png
```

이 명령은 다른 플랫폼용 파일도 함께 만든다. **Windows 전용이므로 쓰이지 않는
것(`android/`, `ios/`, `icon.icns`, `Square*Logo.png`, `StoreLogo.png`)은
지운다.** 남길 것은 `tauri.conf.json`이 가리키는 넷뿐이다.

### 받은 그림에서 고친 것

받은 원본은 알파 채널이 없고 바깥쪽이 **불투명한 검정**이었다. 그대로 쓰면
작업표시줄과 시작 메뉴에서 검은 사각형 안에 아이콘이 든 모양이 된다.
그래서 바깥쪽 검정만 투명으로 바꿨다 — 그림 자체는 손대지 않았다.

새 원본을 만들 때의 규격과 자세한 내용은 `src-tauri/icons/README.md`.

## 11. 배포 전에 반드시 해 볼 세 가지 시험

빌드가 성공했다는 것만으로는 배포물이 온전하다고 볼 수 없다(§5의 `.sig` 사고가
바로 그 예다). 아래는 **사람이 직접 해 봐야 하는** 시험이다.

### ① 신규 설치

인터넷에서 처음 받는 사람의 상황이다.

```
1. 설치파일 실행 → SmartScreen [추가 정보] → [실행]
2. 설치 (관리자 권한을 묻지 않아야 한다)
3. 시작 메뉴 → 방과후 통합 매니저
4. 시스템 화면 → 자료 폴더 경로가 %APPDATA%\kr.school.afterschool 인지
5. 학년도를 만들고 학생 몇 명 넣기 → 정상 저장되는지
```

### ② 자료 보존 확인 (가장 중요)

```
1. ①에서 넣은 자료가 있는 상태로
2. 프로그램 제거 (설정 → 앱 → 방과후 통합 매니저 → 제거)
3. 같은 설치파일로 다시 설치
4. 넣었던 학생과 작업공간이 그대로 있어야 한다
```

여기서 자료가 사라지면 배포하면 안 된다.

### ③ 구버전 → 신버전 업데이트

**2026-09-06에 v0.1.0 → v0.1.1로 실제로 해서 통과했다.**
앱 안 [업데이트 확인] → v0.1.1 발견 → [내려받아 설치] → 앱이 스스로 닫히고
NSIS가 다시 켜서 0.1.1로 열렸다. `%APPDATA%` 자료는 18개 표의 지문까지 동일했고
정산은 낡음이 되지 않았다.

아래는 다음 버전에서 다시 할 때의 순서다.

```
1. v0.1.0 을 Release 로 올린다 → 설치 → 자료를 넣는다
2. npm run version:set 0.1.1 → 커밋 → 태그 v0.1.1 → 푸시
3. Actions 가 끝난 뒤, 설치된 v0.1.0 에서
   시스템 → 업데이트 → [업데이트 확인]
4. 새 버전 안내가 뜨는지 → [내려받아 설치]
5. 프로그램이 스스로 닫히고 잠시 뒤 v0.1.1 로 다시 열리는지
6. 시스템 화면의 버전이 0.1.1 로 바뀌었는지
7. 1에서 넣은 자료가 그대로 있는지
```

5에서 앱이 다시 열리지 않거나 버전이 그대로면 §5의 `relaunch()` 문제이거나
`latest.json`의 `url`이 실제 첨부 파일과 어긋난 것이다.
